Geoapify city-search migration

Connected and verified in development. The owner confirmed Geoapify Free. Published Free-plan terms allow commercial apps and production within quota/feature limits and with attribution. This does not certify the whole app for production or verify private dashboard usage/settings.

1. Implementation

Explicit Search → existing generated API client → GET /api/geocoding/cities?q=… → Express → Geoapify Forward Geocoding /v1/geocode/search, with fixed type=city, English results, JSON format, eight-result limit and no server-IP country bias. The client calls no provider endpoint and carries no provider key.

Normalized fields remain city, country, admin1?, latitude, longitude, timeZone. Decimal coordinates are not swapped or rounded; provider IANA timezone names are validated rather than inferred from current UTC offsets. Unknown/malformed coordinates or zones cannot be selected. Existing saved profiles retain their original coordinates and need no migration or re-geocoding. New selections use the newly selected provider centroid; geocoding is not an exact street-address measurement.

Both birthplace and optional residence use the existing picker independently. State/region, country and timezone distinguish ambiguous matches. Searches still run only on the existing Search action, not while typing/on mount/in the background. Existing abort, stale-response rejection, loading, empty-result and error handling remain. No automatic retries or fallback provider.

2. Credentials, privacy and safeguards

  • GEOAPIFY_API_KEY exists as a server secret and is read only by the server provider module. No EXPO_PUBLIC key, client secret field, public config or committed credential was introduced. No credential value was inspected or printed.
  • Only the typed query is forwarded as user data; all other search parameters are fixed. No saved date/time/profile, residence record, user ID, collection, GPS, browser headers or forwarded client IP goes to Geoapify. Ordinary server connection metadata necessarily does.
  • Query validation: a single q, 2–100 trimmed characters, no control characters or extra/profile parameters. Fixed HTTPS upstream host, redirect refusal, eight-second timeout, response whitelist and no raw upstream errors/URLs exposed.
  • Rate limits: 20 requests/minute per socket peer; maximum two provider calls/second, two concurrent calls, and 2,000 provider calls in a rolling 24 hours per process. Rejected or failed provider attempts still consume that process budget. Invalid input does not call the provider. Safe 429 errors include Retry-After. Forwarded-IP spoofing cannot create fresh buckets.
  • Existing API CORS, no-store, nosniff, body-size/security limits and query-stripping logging remain. Reviewed live logs show route/status, not the city query or provider key. Raw fetch exceptions can contain credential-bearing URLs and are deliberately not logged or returned.
  • Geoapify describes request/technical logging in its policy and generally no more than 24 hours for successful requests; error logging may differ. The app must not promise zero provider or infrastructure logging.

Quota limitation: counters are in-memory, reset on restart and are not shared between replicas or other Geoapify projects/apps. Proxy peers may share the per-peer bucket, as with the existing security model. These limits reduce accidental overuse but are not a durable account-wide billing cap. Owner dashboard monitoring remains necessary; no upgrade, subscription, automatic paid fallback or account configuration change was made.
