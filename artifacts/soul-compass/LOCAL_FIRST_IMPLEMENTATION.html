1. Architectural changes

The root mounts a local profile provider, not an authentication provider. Initial startup reads one validated AsyncStorage record. A missing profile opens onboarding; a saved profile opens existing tabs. Storage failures show an explicit retryable error instead of overwriting data. Cosmos, Crystals, Natal, navigation and visual styling are preserved. Settings offers Profile, Preferences, Privacy and About.

The server still owns Astronomy Engine, historical timezone/DST resolution, Placidus calculations, angles and aspects. No calculation library or paid calculation provider was added to Expo.

5. Authentication removal

No Google, OTP, password, Magic Link, account management, protected-route gate, auth callback or session refresh is part of active navigation. Supabase credentials are not required by this local-first client. Existing credential settings and stored legacy sessions were deliberately left untouched, not read or refreshed.

6. Local record

soul-compass.local.v2 contains schemaVersion: 2, profile, preferences, privacy and optional onboardingDraft.

  • Profile: date, known/unknown birth time, birthplace, optional separate current residence.
  • Preferences: language, crystal collection, intention preferences and hidden crystals. Hidden stones are excluded from recommendations and can be restored.
  • Privacy: calculation consent, policy version, consent timestamp and revocation timestamp.
  • Validation rejects impossible dates/times, invalid coordinates/timezones and malformed records.

Queued writes publish state only after successful persistence. Independent preference/profile/collection updates preserve unrelated fields. Existing language choices remain preferences only; a full translation system was not invented.

7. Migration and existing data

A valid existing v2 record wins. A valid legacy soul-compass.profile.v1 record is copied into v2, retaining the original key and bytes. Older residence-only records become an onboarding draft; residence is never invented as birthplace. Corrupt or future-schema data raises a recoverable error; there is no automatic erase or fallback to a fresh profile. Failed writes leave the previous stored data intact.

No cloud recovery or merge occurs. A cloud-only user without a local birth profile enters a new local profile. All cloud records remain untouched. Local storage is not encrypted; clearing browser/app data or losing a device can lose the profile. OS-level device backups may include application data. No export/import or app cloud sync was implemented.

8. Consent implementation

The versioned explanation appears in Natal and Settings Privacy. I Agree persists permission; it does not calculate automatically. Not Now leaves calculations off. Calculate chart explicitly initiates the request. Consent is checked again immediately at dispatch. The payload includes only date, birth-time status/value and optional DST occurrence choice, birthplace coordinates/timezone, zodiac and house system.

Revocation immediately blocks future requests, aborts active controllers and invalidates late responses. Stale policy versions deny access. Failed consent writes fail closed in the running app. If saving revocation itself fails, the app explicitly warns to retry before closing; it cannot promise the older disk record has changed. There are no offline queues, automatic natal retries or calculation-on-navigation effects. Requests time out after 20 seconds; repeated taps are deduplicated.

Revocation cannot undo data already transmitted before withdrawal. Calculations travel to the existing server, not a new third-party horoscope service.

9. Server privacy

No backend rewrite was needed. Personal profile synchronization has been removed from the active client path. The natal payload excludes residence, names, city/country labels, collection, preferences and account identifiers. The existing calculation engine runs without forwarding birth inputs to an external provider. Existing body-free request logging and no-store/security safeguards remain. Browser city lookup sends only the deliberately typed city string to the existing geocoder; current-sky snapshots send only a UTC instant.

Inspected final web plus iOS/Android bundles: zero matching bundles for secret/admin-key markers, public Supabase configuration references, Supabase domain references, OAuth/OTP methods or /api/me. This is a targeted bundle audit, not a guarantee that arbitrary unknown secret formats could be detected. No credential values were read or printed.

18. Limitations

Internet remains necessary for city lookup and server charts. Local settings work offline after the app is loaded; a cold browser reload without cached assets is not guaranteed because no PWA/service-worker shell exists. Native Expo Go startup and background/foreground behavior require real-device verification. Storage is unencrypted and not synchronized; export/import is deferred. Existing daily horoscope/crystal text remains visibly sample content, not claimed personalized astrology. Natal accuracy retains the existing fixture coverage and explicit historical-time/unknown-time/polar limitations; it is not an independent certification of every house cusp or epoch.
