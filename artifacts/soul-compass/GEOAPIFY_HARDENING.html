B. Quota protection

SettingDefault / behavior
Verified public Free allowance3,000 credits/day; five requests/second; one Forward Geocoding call costs one credit. Owner previously confirmed Free. Other account traffic is not visible to this app.
Internal hard ceiling2,400 credits per UTC day — 80% of allowance. A lower configured allowance reduces the ceiling. Configuration cannot raise it above the reviewed allowance/safety fraction.
Warning / critical1,800 / 2,160 — 60% / 72% of allowance. Crossing flags are saved atomically and logged once per day, even across restarts/instances.
Source limits20 requests/minute; 240 provider credits/day by default per daily keyed socket-peer hash. Existing local 20/minute defense remains supplemental; PostgreSQL is authoritative. Proxy/NAT users may share a bucket; no arbitrary forwarding header is trusted.
Global provider rateThree reserved dispatches per sliding second across instances sharing this database, below the reviewed maximum. Two in-flight calls per process remain an additional resource bound. Unrelated apps/accounts are not included.
Daily resetUTC date from PostgreSQL clock. Global sliding-second dispatch history survives midnight; daily credit/source counters roll over logically on the next request. No background provider request or local-time reset. This is the app's policy; Geoapify's exact billing/reset window was not independently verified.
Conservative accountingReserve one credit in a committed transaction before dispatch. Timeouts, provider errors and ambiguous post-reservation failures retain that reservation. No refund/retry loophole. Invalid inputs, cache hits and coalesced callers do not reserve another credit.
Exhaustion / outageNo new provider dispatch; generic temporary-unavailability 429 or 503, with safe Retry-After where applicable. No budget numbers/keys in client errors. No paid or unrestricted in-memory fallback.

They are not exposed through a public configuration API. Existing supplemental source protection may be stricter than a raised setting.

C. Persistent shared rate limiting

Selected storage: the project's Replit PostgreSQL. Its development instance is free according to Replit documentation; production is usage-billed, explicitly approved by the owner. It is separate from dormant Supabase. No Redis, Upstash, external account or new subscription was added.

  • Persistent across restarts: PASS. Independent replacement Node process inherited exhaustion; actual API restart retained four real reserved credits.
  • Shared across instances: PASS in development. Two separate Node API processes, independent connection pools and distinct test source digests shared one database. One last-credit reservation succeeded; the other was blocked. A separate two-process test verified a global one-per-second test limit with ample daily budget.
  • Atomic reservations: PASS. Transaction-scoped advisory lock and locked state/source rows serialize checks/increments, including the first insert. Not an unlocked read-then-write counter. Conflicting instance ceilings cannot raise the already established daily ceiling.
  • Fail-safe: PASS. Missing/corrupt/unavailable state, connection/statement/lock timeout or clock rollback stops provider dispatch. SQL operations use parameters; no startup-time DDL or automatic production migration.
  • Geoapify production quota: NOT VERIFIED. The public API deployment exists, but no production city search or quota reservation was made during the current audit. Production instances must share the same managed database/policy for the Geoapify cap to hold. Geoapify source identification remains socket-peer based until a trusted proxy topology is independently approved.
  • Astrology global cap: DEVELOPMENT TESTED; NOT PUBLISHED. A dedicated bucket in the existing state table caps combined positions/natal-chart requests at 3,000 per minute across processes. The two-process and replacement-process test passed; production table columns were verified read-only. The source change takes effect in production only after an approved publish.

Tables: geoapify_quota_state (bucket primary key, JSONB operational state) and geoapify_quota_sources (UTC day + keyed source hash composite primary key, JSONB source counters). In addition to Geoapify state, one bucket stores only the aggregate astrology count/limit for the most recent minute window; it has no user/device/IP key and resets when a request arrives in a later window. If the app is idle, that single non-personal count may remain until the next request. No profile, birth data, city query, credential or raw IP is stored. Geoapify source hashes are keyed using a domain-separated server secret and UTC day, never logged, and expired-day rows are deleted on the next admitted operation. If no further traffic occurs, deletion waits for that next operation; no hard wall-clock deletion promise is made.

At most five database connections per API process; two-second connection and lock bounds and 2.5-second statement timeout. Source-admission traffic has a global 12,000/day ceiling to bound counter growth; cache keys/results have an independent bounded memory lifetime. Database/instance usage still needs monitoring and conservative deployment capacity settings.

D. Privacy, security and efficiency

Data flow remains explicit typed query → existing Express endpoint → fixed Geoapify city endpoint → sanitized coordinates/IANA timezone. No saved profile/date/time/residence/GPS/device identifier or client headers/IP is forwarded. Normal server connection metadata reaches Geoapify. Geoapify/OpenStreetMap attribution and provider privacy links remain. Settings now discloses the short-lived anti-abuse hashes/counters.

Cache: per-process, five minutes by default, configurable up to one hour or disabled, maximum 256 entries. Case/surrounding whitespace normalized; cache keys are HMAC digests rather than raw queries. Results retain exact coordinates. Concurrent identical misses coalesce within each process. Successful empty results can be cached; errors are not. Across processes, identical misses may independently dispatch, but every dispatch is atomically metered. Shared cross-process caching was intentionally not introduced.

Operational logs contain event names and counts, not source digests, queries, birth data or credentials. Threshold flags remain in PostgreSQL even if a process dies before emitting its log event. No analytics, tracking, external notification channel, cloud profile sync or public admin surface was added. The astrology calculation and consent logic are unchanged; the request-capacity guard is shared through PostgreSQL.
